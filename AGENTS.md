## 1. Mission and immutable product boundaries

Nassaq is a free/open-source, privacy-first, browser-only CSV-to-XLSX validation/conversion app for Arabic and English users. Its job is to prevent accidental data changes when a person prepares CSV for Excel. **CSV input only**, one static page, no backend/database/auth, no server upload, no analytics, no AI, no external requests carrying any part of a selected file. Process in browser; generate XLSX only after full validation. Arabic is the default UI language and works RTL; English works LTR.

The MVP caps are **2 MiB input, 10,000 data rows, 50 columns, 100,000 data cells, 32,767 UTF-16 units per cell**. No partial successful export when limits are exceeded. The code should offer clear human-readable refusal.

## 3. Technology and architecture

**Chosen:** Vite + React + TypeScript strict, Tailwind CSS v4, selected shadcn/ui components, i18next/react-i18next, Papa Parse, ExcelJS *subject to phase-0 browser/security spike*, dedicated module Web Worker, Vitest, Playwright, Lucide React. **Not chosen:** Next.js App Router, next-intl, backend, ORM, database, authentication, remote import API, analytics. Deploy static `dist/`.

Phase 0 must confirm ExcelJS worker browser compatibility, `xlsx.writeBuffer`, `xlsx.load`, exact literal `""` empty string, Arabic text and formula-looking strings, and dependency/licensing audit. **Do not implement user features if this gate fails.** Document an approved alternative first.

Recommended logical boundaries: `src/app` for React state; `src/components/import` for UI; `src/i18n` for locale resources; `src/domain` for pure rules; `src/worker` for decoding/parsing/ExcelJS orchestration; `src/lib` for worker client and filename/download helpers; `tests/fixtures` and `tests/e2e` for synthetic tests.

Use typed messages with `jobId`; worker retains full parsed table, main UI gets ≤20 preview rows and summary. Cancel/reset terminates worker, ignores stale results, revokes download object URL. Only a `READY` message following complete XLSX read-back enables download.

## 4. Non-negotiable data rules

1. **Never silently modify values.** No trimming, case folding, whitespace reduction, Unicode normalization, date inference, Arabic-Indic digit conversion or `Number()` by default.
2. Read CSV as raw bytes and user-approved encoding. Accept UTF-8 BOM and strict UTF-8; allow manual Windows-1256/ISO-8859-6; never decode invalid UTF-8 by replacement without informing user.
3. Require explicit review where encoding or delimiter is uncertain; reprocess from immutable original bytes on option changes.
4. Parse CSV using Papa Parse `header:false`, `dynamicTyping:false`, no transforms, no row-skipping; arrays of strings preserve duplicated header labels and field positions.
5. **Text is the default export type of all columns.** Literal Excel text for `0005`, 20-digit IDs, date-shaped codes, phone-like strings, Arabic names, spaces, newlines, empty values, `=1+1`, `+SUM(...)`, `-...`, `@...`.
6. **Never interpret untrusted CSV content as an Excel formula.** No `{ formula }`, hyperlinked/autogenerated expressions, macros or external references.
7. `Number` is explicitly selected per whole column and must satisfy the restrictive grammar, safe-integer/significant-digit rules and lexical round-trip check from `04`. Reject unsafe column conversion, don't partially convert or round silently. No Date type in MVP.
8. Preserve every CSV record (except parser's provable phantom record for a terminal delimiter) and every column; no silent uneven-row padding or truncation. Empty string is distinct from absent field. A header label stays an exported row.
9. For every generated workbook, reload the XLSX, compare every cell value, type, dimensions, formula and hyperlink absence to the approved data. **If any mismatch, block the download.**
10. All errors should be safe, localized and actionable, identifying row/column when possible without logging the user's private data.

## 5. Security and privacy constraints

- User file bytes, CSV cells, filenames, generated workbook and personal data **must never** be transmitted to a server or third-party API. No analytics, telemetry, crash reporting, remote fonts, CDN runtime script or user-data persistence.
- Avoid any unsafe HTML insertion, eval, dynamic JavaScript, CSV-derived URL or remote resource loading. Render as escaped React text with bidirectional isolation.
- Apply raw-byte, row, column, cell-count, cell-length caps before unbounded work. One active worker job only; make cancellation possible.
- Sanitize output filename; output constant sheet name `Data`; no HTML/XLSX links from input.
- Review new dependencies for purpose, license, vulnerabilities and client bundle/runtime impact. Do not introduce unnecessary packages. Keep lockfile and audit findings documented.
- Privacy marketing may claim *file content stays on device* after proving with network tests; never claim zero web traffic or absolute security.
- Do not log CSV content to console, analytics, error trackers, or automated tests with real records. Only synthetic fixture data.

## 6. Code conventions

- TypeScript `strict:true`; avoid `any`, unchecked casts and non-null assertions. Model errors as discriminated unions. Validate all worker messages and external inputs at boundaries.
- Prefer functional pure domain utilities for encoding candidate evaluation, delimiters, risk classification, numeric eligibility and manifest comparison. Keep vendor logic in adapters.
- React components small and single-responsibility; native HTML semantics first; shadcn only when it offers real value. No global state library unless React state becomes demonstrably insufficient.
- `PascalCase.tsx` React components, `kebab-case.ts` or consistent project-established conventions for utilities; named exports except entry components if scaffolding requires otherwise.
- Use explicit stable error codes such as `DECODE_FAILED`, `MALFORMED_CSV`, `INVALID_NUMBER`, `VERIFY_FAILED`; render via translations, not hardcoded English error strings.
- Never mutate domain table in place after it has been approved; keep raw original values accessible for export/verification only within the active job.
- No SSR, API routes, database, server actions or background cloud processing. No dependency added solely for convenience without a documented reason.

## 7. Localization and accessibility

- Arabic default; English toggle; `html.lang`, `html.dir` synchronized. Source data must remain byte/codepoint-equivalent regardless of UI locale.
- All user-facing copy resides in Arabic and English translation dictionaries; meaningful placeholders and examples localized without modifying file values.
- CSS logical properties and bidirectional isolation (`<bdi dir="auto">` or equivalent) for displayed file contents; no forced Latin phone-number transformations.
- Label inputs, preserve keyboard navigation, show visible focus, use `aria-live` for processing, and never encode warning state by color alone.
- Preview at most 20 records; the entire file still undergoes checks before export.

## 8. Test and release obligations

For a parser/encoding/integrity change, add synthetic byte fixture and test **downloaded/reloaded XLSX**. Minimum fixtures: UTF-8 BOM/non-BOM, Windows-1256/ISO-8859-6, Arabic names, Arabic-Indic digits, leading zeros, >15-digit IDs, date-like codes, quoted delimiters, multiline text, nested quotes, empty strings, formula prefixes, inconsistent rows, malformed encoding, long cells and file/count limits.

Before a phase is marked Done: typecheck, unit/integration fixtures, targeted Playwright E2E, production build and relevant browser smoke pass; show modified file list and tests/results. For public release, include Chrome/Edge/Firefox/Safari, local-network intercept, dependency/license review, and no critical workbook mismatch. A successful preview or an XLSX that simply opens is **not sufficient** verification.

## 9. Phase discipline and communication

1. Inspect repo and git status; **preserve existing implementation**. See `docs/XLSX_WORKER_FEASIBILITY.md` for initial inspection and current feasibility evidence; verify the current state rather than assuming it is unchanged.
2. Work on **only the phase explicitly authorized** in `08_IMPLEMENTATION_PLAN.md`; read phase dependencies and acceptance gates first.
3. If a decision is blocked (e.g. ExcelJS browser bug, empty string not preserved, risk discovered), stop and report it rather than workaround by losing data or bypassing tests.
4. Write/update tests with each behavior. No unsupported dependencies or architectural rewrites.
5. Update affected docs in the same change, with a short decision note. Never assert passing tests without having run them.
6. Report summary, files modified, commands executed, pass/fail results, known limitations and next suggested phase. **Do not start the next phase automatically.**

**Definition of Done:** a phase satisfies its acceptance cases and tests; no unapproved scope; all data-integrity and privacy invariants remain satisfied; source/docs/tests agree.

Create/switch to the task branch before editing when Git is available; do not work directly on `main` or `master`. Do not reset, stash, discard or overwrite user changes to make branching convenient.
- Plan a small set of coherent commit checkpoints before a multi-step implementation. Group changes by purpose, not by file type or tool call: keep a behavior, its regression tests and directly related documentation together. Separate independent tooling, behavior and documentation-only changes when each group is meaningful on its own.
